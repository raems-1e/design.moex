# MOEX Design — версия для внутреннего контура

Версия: 1.0.0-internal.1. Подготовлено 27 октября 2026 года.

Четыре статические страницы: главная, коммуникационный дизайн, продуктовый дизайн,
материалы. Фронтенд: HTML, CSS и JavaScript без фреймворков. Сервер раздачи:
Node.js 24, только стандартные модули. NPM-зависимостей нет, `npm install` не нужен.
При запуске и работе зависимости из интернета не скачиваются.

## Быстрый запуск

Требуется Node.js 24.x. Из корня репозитория:

```sh
sh check.sh
npm start
```

Открыть http://localhost:8080. Проверка: `curl -i http://localhost:8080/health`.
Ожидается HTTP 200 и `ok`. Без npm: `node app/server.mjs`.
Сайт не требует компиляции; `npm run build` выполняет автоматические проверки.
На этапе сборки CI нужно разрешить тесту временный loopback-порт.

## Контейнер

```sh
docker compose up --build -d
docker compose ps
curl -i http://localhost:8080/health
docker compose down
```

По умолчанию Compose публикует порт только на 127.0.0.1. Для внешнего доступа
используйте утверждённый ingress. Например, корпоративная платформа запускает
образ с containerPort 8080 и HTTP probe `/health`.

Образ работает от непривилегированного пользователя node. Compose включает
read-only filesystem, drop ALL capabilities и no-new-privileges.
Контейнер не выполняет установку пакетов при запуске.

Перед сборкой внутри контура DevOps должен указать утверждённый образ Node 24
из корпоративного registry, желательно с digest:

```sh
docker build --build-arg NODE_IMAGE=registry.example.internal/node:24-alpine -t moex-design:1.0.0-internal.1 .
```

Адрес выше — пример, его нужно заменить реальным. Образ должен иметь `node`,
пользователя `node` и совместимую структуру прав. Публичный `node:24-alpine` —
только стандартное значение для локальной сборки, не требование доступа
в интернет из рабочего контейнера. Сканирование и закрепление версии образа —
за DevOps/ИБ. Docker build/run в среде подготовки не проверены: daemon не запущен.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---|---|
| PORT | 8080 | Порт Node-сервера и Compose |
| HOST | 0.0.0.0 | Интерфейс при прямом запуске Node |
| BIND_ADDRESS | 127.0.0.1 | Привязка опубликованного порта Compose |
| NODE_IMAGE | node:24-alpine | Базовый образ на этапе сборки |

Все значения задаются окружением платформы. `.env.example` — документация,
создавать `.env` для запуска необязательно. Если нужен локальный файл, Node 24
можно запускать `node --env-file=.env app/server.mjs`. Секретов приложению не нужно.
В Compose HOST фиксирован 0.0.0.0 внутри контейнера.

Сайт рассчитан на корень выделенного домена. При публикации под URL-префиксом
DevOps должен настроить ingress и проверить относительные ссылки отдельно.

## Защита и внешние подключения

Сервер отдаёт CSP, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer,
X-Frame-Options: DENY, Permissions-Policy на всех ответах.
`frame-ancestors 'none'` запрещает встраивание страницы в iframe. Если портал
требует iframe, точный список доверенных origin и согласованную политику
необходимо получить у ИБ, не заменять запрет на `*`.

CSP разрешает скрипты и шрифты только с собственного origin, запрещает
inline JavaScript и eval. Inline скрипты вынесены в src/assets/internal/.
Для CSS сохранён `style-src 'self' 'unsafe-inline'`: существующие стили,
SVG и анимации используют style-атрибуты. Это ограниченное исключение только
для стилей, не для JavaScript; требуется согласование ИБ.
Изображения `data:`/`blob:` разрешены для SVG-декора и клиентского скачивания.

Шрифты полностью локальные. Историческое CSS-имя Manrope теперь является
алиасом локального Inter: буквы и цифры используют один шрифт. Метрики могут
слегка отличаться от прежнего Manrope; нужна финальная визуальная приёмка.
Лицензия Inter сохранена в src/assets/fonts/inter/LICENSE.txt.

Приложение не подключается к БД, API, очередям, SMTP, SSO или LLM-шлюзу.
Пользовательской регистрации, логина, сессий и ролевой модели нет.
Если доступ к сайту должен быть ограничен сотрудниками, корпоративный SSO
обеспечивается ingress/порталом, а не этим статическим приложением.
В коде есть внешняя ссылка `https://moex.com/privacy` — это переход по нажатию,
не загрузка зависимости. При необходимости заменить её на согласованный
внутренний адрес политики конфиденциальности.
TLS и HSTS настраиваются на корпоративном ingress, который не должен удалять
защитные заголовки приложения. `/health` должен быть доступен probes.

## Контент и персональные данные

Фотографии, имена и должности сотрудников являются размещённым контентом.
Приложение их не собирает у посетителя, но публикует; разрешение на такое
размещение должен подтвердить владелец контента. Не отмечать «персональных
данных нет» только из-за отсутствия базы данных или входа.

Ссылки на скачивание материалов остаются незаполненными, как в исходной версии
(src/assets/materials/downloads.js). Это отдельная контентная задача владельца,
не подключение к внешним системам. Не заявлять, что все материалы доступны.

## Структура

- src/ — только публичные файлы четырёх страниц и ресурсов
- app/server.mjs — HTTP-сервер, security headers, healthcheck
- tests/ — тесты маршрутов, заголовков, ресурсов и метаданных
- check.sh — проверка синтаксиса и тесты
- Dockerfile, compose.yaml, .env.example — запуск и конфигурация
- CLAUDE.md, rules/ — правила сопровождения
- docs/ — отчёт адаптации, метаданных, комментарий для размещения

Каталог public/ и конфиги Vercel в поставку не включены. `.git`, `.vercel`,
локальные `.env` и история Git также не включены. Исходный публичный репозиторий
не изменён. Для импорта этого архива не требуется сохранять старую структуру
со страницами в корне: используйте структуру src/ + app/ из поставки.

## Перенос в GitLab

1. Создать ветку от актуальной main внутреннего `vibe-portal/vibe-intake/moex-design`.
2. Перенести файлы этой поставки в корень репозитория, удалив старые дубли страниц,
   assets/, public/, vercel.json и .vercelignore. Не удалять служебную .git,
   корпоративную .gitlab-ci.yml или настройки сканеров платформы.
3. Проверить diff; выполнить `sh check.sh`, сборку контейнера и браузерный smoke-test.
4. Создать merge request; повторить проверки портала и дождаться согласования.
5. Отметить чек-лист и закрыть техдолг README после подтверждения в контуре.

Перечень файлов стартового пакета из скриншота добавлен, но официальный шаблон
и внутренние проверки портала не предоставлены. Соответствие его полным правилам
может подтвердить только повторный прогон CI, а не наличие файлов само по себе.

## Ответственность

Владелец контента и приёмки: команда MOEX Design (конкретного ответственного
указать в карточке решения). Публикация, ingress, базовый образ и мониторинг:
команда размещения/DevOps. Политики защиты и согласование исключений: ИБ.
Мониторинг — HTTP GET /health, логи старта/ошибок идут в stdout/stderr.
Логин, пароли, аналитика посетителей и cookies приложением не создаются.
